# SESSION-2026-10-30-E86-A-FIX14

## §1 — Contexte

Correction de l'erreur HTTP 400 sur l'analyse d'image (vision) via Groq. Le chat texte fonctionne (modèle `openai/gpt-oss-120b`), et le modèle de vision a été basculé vers `meta-llama/llama-4-scout-17b-16e-instruct` (E86-A-FIX12), mais l'erreur 400 persiste lors de l'analyse de photos. Le format de requête (messages `user` en tableau de blocs `text`/`image_url`, pas de message `system`) a été vérifié conforme (E86-A-FIX13). Cette session passe les images en **base64** avant envoi à Groq, afin d'éviter les timeouts côté Groq lors du téléchargement des URLs Cloudinary.

## §2 — Diagnostic

- `src/core/ai-engine/skills/vision/vision.ts` envoyait les images par leur **URL Cloudinary** (`image_url: { url: '<cloudinary-url>' }`).
- Groq doit **télécharger l'image depuis l'URL** avant de l'analyser. Si l'image est volumineuse (2-3 Mo) ou si Cloudinary répond lentement, Groq abandonne et renvoie une erreur `400` avec le message *"Error fetching url: request timed out"*.
- Avec des images légères (200-300 Ko), la requête fonctionne. Ce n'est donc pas un problème de modèle ni de format de requête, mais un problème de **téléchargement d'URL côté Groq**.
- Solution : télécharger l'image côté serveur (Next.js), la convertir en base64, et l'envoyer directement dans la requête au format `data:image/jpeg;base64,...`.

## §3 — Corrections

### 3.1 `src/core/ai-engine/skills/vision/vision.ts`

Nouvelle fonction utilitaire `loadImageAsBase64` qui :
- Télécharge l'image depuis son URL (`fetch` avec timeout 15s).
- Vérifie le statut HTTP et le Content-Type.
- Limite la taille à **5 Mo** (`MAX_IMAGE_BYTES`) pour éviter les timeouts.
- Convertit le contenu en base64 (`Buffer.from(arrayBuffer).toString('base64')`).
- Retourne une URL `data:${contentType};base64,${base64}` ou un warning en cas d'échec.

Dans `detectPartType` :
- Chaque URL est chargée et convertie en base64 avant d'être ajoutée au `content`.
- Les images inaccessibles, trop volumineuses ou en erreur d téléchargement sont **ignorées** avec un warning explicite, sans bloquer les autres images.
- Si aucune image valide n'est disponible, un `VisionResult` est retourné avec `detectedType: null` et le warning « Aucune image valide pour l'analyse ».
- Les warnings de chargement sont propagés aux warnings de Groq.

Avant (extrait) :
```ts
for (const url of input.photoUrls.slice(0, 3)) {
  content.push({ type: 'image_url', image_url: { url } });
}
```

Après (extrait) :
```ts
for (const url of input.photoUrls.slice(0, 3)) {
  const loaded = await loadImageAsBase64(url);
  if (loaded?.warning) {
    warnings.push(loaded.warning);
    continue;
  }
  if (loaded) {
    content.push({ type: 'image_url', image_url: { url: loaded.url } });
  }
}
if (content.length === 1) {
  return {
    detectedType: null,
    confidence: 0,
    rawResponse: '',
    warnings: [...warnings, 'Aucune image valide pour l analyse'],
  };
}
```

Le modèle de vision reste `meta-llama/llama-4-scout-17b-16e-instruct` (E86-A-FIX12).
