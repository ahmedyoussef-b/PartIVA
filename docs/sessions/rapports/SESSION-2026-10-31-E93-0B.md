### 6.1 Contraintes machines (disponibilité, maintenance)

- Le modèle `Machine` ne comporte pas de champ "capacité maximale" ou "occupancy". Le champ `capacity` côté interface est affiché `"—"` par défaut et n'est pas relié à une logique de disponibilité.
- Le statut `MachineStatus` (IDLE / RUNNING / MAINTENANCE / OFFLINE) est exploité dans l'interface mais **n'est pas vérifié en temps réel** lors d'une recommandation. Une machine affichée en `IDLE` peut en facture être en maintenance hors ligne.
- **Risque** : recommander une machine qui est techniquement disponible en BDD mais qui est en réalité en maintenance non enregistrée.

### 6.2 Tests existants

- Les tests sur le parc machines dans `e2e/protected-pages.spec.ts` (lignes 7‑9) vérifient les pages `/admin/machines`, `/admin/materials`, `/admin/parametres`.
- **Aucun test** ne vérifie le matching piece ⇄ machine (aucune fonction n'existe encore).
- Le test `part-completeness.spec.ts` vérifie la complétude des champs `Part` mais pas la cohérence avec les machines.

### 6.3 Recommandations de prudence

1. **Afficher "Aucune machine recommandée"** plutôt que de suggérer un mauvais match quand les champs requis (`material`, dimensions minimales) manquent.
2. **Vérifier le statut `RUNNING` / `MAINTENANCE`** avant d'afficher une recommandation : si aucune machine n'est en `IDLE`, afficher "Toutes les machines sont actuellement occupées ou en maintenance".
3. **Ne pas stocker la recommandation en BDD** d'elle-même ; afficher seulement en interface utilisateur (UI-transient). Si persistance nécessaire, le faire via un champ `suggestedMachineId` sur `Part` mais en marquant cela comme "non officiel" jusqu'à validation humaine.
4. **La recommandation doit fonctionner hors quota IA** : la logique heuristique ne dépend pas d'un appel LLM, elle doit donc fonctionner même quand le quota est atteint.

### Recommandation : règles heuristiques vs LLM

| Approche | Avantages | Inconvénients |
|---|---|---|
| **Règles heuristiques simples** | - Déterministe, pas de dépendance externe<br>- Rapide à implémenter, coûts nuls<br>- Ex: "Si material = TITANE et Machine.type = CNC → recommander machine X" | - Couverture limitée<br>- Difficile à maintenir si les règles grossissent |
| **Appel LLM (Groq)** | - Peut raisonner sur des descriptions libres<br>- Peut suggérer des machines "proches" quand aucun match exact n'existe<br>- Réutilise l'infrastructure IA (Groq) | - Coût par requête (même si gratuit dans le MVP)<br>- Latence réseau<br>- Non déterministe<br>- Surcharge supplémentaire sur le quota IA (le problème initial) |

**Verdict :** Pour la première version (E93), privilégier **des règles heuristiques simples** basées sur :
1. Correspondance `material` (texte exact ou contient un mot-clé)
2. Correspondance `PartSpecification` de type "diamètre", "longueur", etc. avec tolérance
3. Type de machine `MachineType` (CNC, LATHE, PRINTER_3D)

Aucune fonction de matching n'existe dans le code actuel — il faudra en créer une nouvelle.
