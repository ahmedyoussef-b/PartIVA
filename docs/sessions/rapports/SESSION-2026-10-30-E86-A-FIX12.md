# SESSION-2026-10-30-E86-A-FIX12

## §1 — Contexte

Correction de l'erreur HTTP 400 sur l'analyse d'image (vision) via Groq. Le chat texte fonctionne (modèle `openai/gpt-oss-120b` actif), mais l'analyse de photo renvoyait une erreur 400 (Bad Request), bloquant l'ingestion d'images.

## §2 — Diagnostic

- `src/core/ai-engine/skills/vision/vision.ts` appelait Groq avec le modèle `qwen/qwen3.8-27b` (défaut codé en dur, ligne 29).
- Le format de requête `{ type: 'image_url', image_url: { url } }` est correct (OpenAI-compatible, supporté par Groq).
- Le modèle `qwen/qwen3.8-27b` n'est pas un modèle vision actif sur Groq : le modèle est trouvé (pas de 404) mais rejette la requête contenant des images (400 Bad Request).
- Le chat texte fonctionne car il utilise `openai/gpt-oss-120b` (modèle texte uniquement), tandis que la vision nécessitait un modèle multimodal.

## §3 — Corrections

### 3.1 `src/core/ai-engine/skills/vision/vision.ts` (ligne 29)

Avant :
```ts
model: process.env.GROQ_VISION_MODEL || 'qwen/qwen3.8-27b',
```

Après :
```ts
model: process.env.GROQ_VISION_MODEL || 'meta-llama/llama-4-scout-17b-16e-instruct',
```

Le modèle `meta-llama/llama-4-scout-17b-16e-instruct` est un modèle vision confirmé sur Groq, supportant le format OpenAI-compatible `{ type: 'image_url', image_url: { url } }`.

Le format de requête (texte + tableau `content` avec `image_url`) et le prompt système sont conservés inchangés (déjà conformes au format OpenAI/Groq).

### 3.2 `.env.example` (ligne 134)

Avant :
```
GROQ_VISION_MODEL=qwen/qwen3.8-27b
```

Après :
```
GROQ_VISION_MODEL=meta-llama/llama-4-scout-17b-16e-instruct
```
